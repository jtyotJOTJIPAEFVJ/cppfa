# Module optimizer: how it works

The optimizer (`fitengine::opt::optimize`, `src/Optimizer.h/.cpp`) finds the best modules for the open mid, low, rig and high slots of a fit for one goal. It is built on the fit engine (`FIT_ENGINE.md`); pyfa runs it as a separate process through a JSON request (`OPTIMIZER_CLI.md`, `src/Request.h/.cpp`).

## 1. Overview

**Goals:** the engine's goals (`FIT_ENGINE.md`, section 1): EHP of a layer, effective sustainable repair, resists only, outgoing remote repair, and the balanced local + remote goals. The damage profile is uniform.

**Racks:** mid, low and rig by default; high slots only for remote repairers (no weapons: hardpoints aren't tracked). Requests open individual slots (modules or empty slots); every other module is pinned with its state, charge and mutations.

**Constraints** (`Options`, request fields in `OPTIMIZER_CLI.md`): price cap per module, officer modules, ancillary repairers, capacitor boosters, the most repairers of the goal, capacitor stability, a minimum capacitor recharge. A set that misses a constraint doesn't count as fitting.

**Pipeline**, in short. Brute force is out of reach: a battleship has billions of core sets times thousands of resist sets each. So:
- **Stage 1** searches with one representative per subgroup of similar modules and a separable model of the goal, `V(core modules, their capacitor use) / D(resist modules)`, built from engine measurements. Branch and bound with exact upper bounds keeps most combinations from ever being scored.
- **Stage 2** lets every slot of the best stage-1 sets try the other members of its subgroup, evaluated exactly with `SearchPlan`.
- **Refine** searches every module choice of each rack (across subgroups and roles, with single and pair moves and an iterated local search), exactly, until it converges or the time budget is used.

Every reported option is an exact engine evaluation. The model only drives the search.

## 2. Pipeline

`Search::run()` in `Optimizer.cpp`:

1. **setup**: modules in searched racks become open; everything else is pinned (`base_`). Slot counts come from the engine's modified `medSlots`/`lowSlots`/`rigSlots`/`hiSlots`. With `Options::partial` (requests), only the flagged modules and requested empty slots are open; a rack's open count is its requested slots, at most its free slots (rack size minus the rack's pinned modules) and `maxSlots`. A pinned module's state goes through `clampPinnedState` (also in the start fit; `Result::clamped` lists them).
2. **gatherCandidates**: every published module for each searched rack, filtered by canFitShipGroup/Type, capital size, rig size, weapons in high slots, officer (metaGroup 5), the constraints, module rules (`excludedFromSearch`), price cap, maxGroupFitted/maxTypeFitted vs pinned, `Engine::reach`, and the shield-active skip list (Capacitor Power Relay). Modules that need a charge (ASB, AAR, cap booster) get one candidate per valid charge; candidate prices include the charge (the cap applies to the module). Abyssal modules in opened slots are offered back as they are (`addMutatedCandidates`: at no price, at most as often as the fit has them); new abyssal modules are never proposed.
3. **measure**: each candidate alone on the pinned fit (chunked one-slot SearchPlans): goal gain, divider drop, HP gain, capacitor budget gain, output gains, own fitting, unconstrained repair (`rep`), resonances changed (`resMask`) and ship fields changed (`shipChanged`). The best charge per charge-needing module is kept; the others go to `chargeAlts_` for refine.
4. **interactions**: provisional subgroups (rack, group or rig family + calibration cost, resMask, size token from the name), representative = directly strongest. Rigs are split by calibration cost: with only the dearer T2 representative, stage 1 misses sets where only the T1 rig fits. One SearchPlan with all representatives gives each subgroup's influence. Pair gains (amplifiers, rigs that modify repairers or costs) are measured for every member of an influencing subgroup against each influenced representative.
5. **classify**: useless members drop. Roles per subgroup:
   - **resist**: changes only resonances alone, no pinned writes, and only influences other resist subgroups (fixed point; the RAH adapts to everything)
   - **fitting**: changes only outputs, influences nothing, uses no capacitor
   - **core**: everything else (all rigs are core)

   Members are sorted by a role-specific strength tuple, ties to the cheaper one (rigs: dearer).
6. **buildKinds / buildCorePlan**: one kind per subgroup (its representative). The core plan has every core kind in every slot of its rack, with influence enabled. It yields each kind's influencers (`inflKind_`), pinned influencers, and the kinds that change capacitor (`inflCap_`), HP (`inflHp_`), resists (`eps_`) and outputs (`inflFit_`).
7. **Records (the separable model)**: per-module `ModuleStats` keyed by the counts of only its influencers, plus cap peak and HP keyed the same way. Each is computed once with a core-plan evaluation and cached (`Cache<V>`). `assemble(counts)` builds a core's module list and its `RepProfile`, so V(core, x) = `profile.repair(layer, x)` uses the engine's own code. The capacitor budget record (`budgetRecord`) is composed from the module and cap-peak records without an engine call of its own. Fitting records per (output-influencer key, fitting set); `fitSlack` is cached per (output-influencer key, free slots).
8. **Resist tables (lazy)**: one `ResistTable` per `eps_` key (the counts of the core kinds that change resists).
   - **Bounds** (`resistBounds`): the engine reports how it composed the layer's four resonances (`TestDetail::resonanceParts`). One test with only the eps modules gives the base value, preIncrease, unpenalized multiplier, postIncrease and the penalized multipliers with their penalty groups. One test per resist kind (eps modules + that kind) gives the kind's own multipliers: the list difference. Every resist set's D then follows pyfa's formula (sorted per penalty group and direction, `1 + (m-1)·exp(-i²/7.1289)`). It is computed in double during one depth-first walk over the rack multisets (each extends a prefix of the previous one; subtrees that don't fit next to the eps modules are skipped) and padded by 1e-5 to a lower bound.
   - **RAH**: the reactive hardener (the only resist kind other resist kinds influence) adapts. Its four resonances are some split of its total resist T (the adaptation conserves T, each type within [1-T, 1]). Each resonance, and so D, is concave in its multiplier, so D's minimum over that set is at a vertex: all of T on one damage type. The bound is the min over the four vertices.
   - Anything else (forced values, preIncrease/postIncrease changes, an eps multiplier that disappears, single-kind reconstruction off by > 1e-6, another adaptive kind, > 8 multipliers per kind and type) makes `resistBounds` fail; that table is then evaluated in full (`OPT_NO_ANALYTIC=1` forces it). No table has needed it so far.
   - **Exact records** (`resistRec`): a set's exact D, capacitor use and costs come from the resist plan (one engine call) when first needed, stored in lock-free chunks.
   - **Orders** (`ResistOrder`, per (eps key, free slots)): the table's sets grouped by rack size vector, each group sorted by bound (stable radix sort). `resistAt(order, i)` materializes the order on demand by merging the groups that fit and evaluating each set as its bound comes up. An evaluated set is emitted once its exact D is below every pending and in-flight bound, so the result equals sorting all sets by exact D (stable, ties by set index). Threads that need the same order evaluate its pending sets concurrently (`stepOrder`).
   - Every exact evaluation checks D >= bound and counts violations (log line "resist tables: ... bound violations"; a warning in `Result::warnings` if > 0). With `OPT_RESIST_VERIFY=1` (or `bruteForce`) every set is evaluated at build and checked.
9. **stage1**: best-first branch and bound, fixing one rack per level.
   - **Rack order**: the rack holding most of the goal's own modules, then rigs, then a balanced goal's other goal rack, then the rest (`OPT_RACK_ORDER` overrides it). Order matters a lot: a partial set's bound takes the free racks at their best independently, so racks that decide the most (repairers, rigs) should be fixed early, but each fixed rack multiplies the nodes by its multiset count. Measured spreads between orders were up to 16x, with different winners per case.
   - **Dive**: until K sets are kept, nodes come depth first (best child first) from a stack, so cores are scanned early and the cutoff rises. Every node is still expanded or pruned against a true K-th score.
   - **Partial node bound** (`partialBound`): every split of each free rack's slots between value and resist side. Value side: HP or the capacitor budget, maximized per projection size; repairer items at their best stats over all influencer projections; min of the capacitor, slot, CPU and power knapsack relaxations. Resist side: min D over eps projections. The value-side inputs are memoized: `projTable(what, fixed, freeMask)` per (fixed counts of `capAll_` / `inflHp_`, free racks), `repItem(kind, side, fixed, freeMask)` per (fixed influencer counts, free racks, side).
   - **Fitting prefilters**: a serial child filter (cheapest cost of pinned + parent + the rack's multiset vs the output bound); `partialFits` (fixed modules at cheapest vs `nodeOutputMax`: the fixed core modules' own output bonuses plus the strongest output modules in the slots still free); `fixedFits` (when no kind in the free racks changes outputs or the fixed modules' costs, the fixed modules' measured costs must fit within `fitSlack` of the free slots: it holds for every completion, since added modules only cost more and leave fewer free slots). Then `fitSlack` and `feasibleMinD` (core bound uses the best D among resist sets that leave room to fit).
   - **Core scan**: resist sets by D; score = V(core, x(R)) / D(R); fitting check with fitting-module sets; top-K heap (K = 200).
   - **Batches**: the top of the queue is processed in mixed batches of fixed size (up to 64 partial nodes, 4,096 children or 512 whole cores) in one parallel loop. Scans run against the cutoff at batch start plus their own finds, then merge into the top-K in queue order with the live cutoff, which keeps exactly what a sequential scan would. Batch sizes are constants, so results don't depend on the thread count; they can differ from a strictly sequential search only in ties at the K-th score.
   - The queue is a vector heap, compacted (nodes at or below the cutoff dropped) whenever it has doubled.
   - **Time cap**: with `timeBudget` > 0, stage 1 stops at half of it; stage 2 and refine go on from the sets found so far (`stats.stage1Stopped`, a warning).
   - `--verbose` prints a progress line every 2 s (nodes per level, queue, top bound, cutoff).
10. **stage2**: per stage-1 set in score order, one SearchPlan with each slot's subgroup members as options. Exact local search: single swaps, then pair swaps; key (valid, fits, goal bucket, -price), where the goal bucket is `floor(log(goal) * 1e7)` (goals <= 0 or NaN share the lowest bucket), so goals within ~1e-7 relative compare by price. The key is a strict weak order, so every accepted move strictly improves it and the search ends (a goal tolerance isn't transitive and made stage 2 cycle forever); a cap of 10,000 accepted moves per starting set is a backstop that adds a warning. Memo by sorted candidate ids. Stops after `patience` (50) starting sets without improving the best fitting set. Starts run 16 at a time in parallel; each sees the memo of the earlier batches plus its own, and the patience rule is applied afterwards in start order (deterministic). It also records the max relative error of the model vs the exact score of each starting set (0 on every test so far).
11. **refine**. Stage 1 sees one representative per subgroup and stage 2 swaps members only within a slot's subgroup, so a weaker, cheaper-to-fit member (a compact damage control, 'Posse' hardeners, Syndicate plates), a different charge or a trade across subgroups is never tried there. Without refine, the pipeline missed the exhaustive member-level optimum in 10-13 % of small requests (by up to 35 %) and was below the best known set in 7 of 19 whole-rack test cases (by up to 15 %). Refine searches every module choice of each open rack:
    - **Choices** (`buildPool`): every useful member of every subgroup (any role) plus the non-best charges (`chargeAlts_`). Dominated choices are dropped: another choice of the same subgroup at least as strong in every measured effect (goal gain, divider drop, HP, capacitor, outputs, repair, pair and cost gains, pinned cost drops, own cap use) and at most as expensive in CPU, power, calibration and ISK, with no tighter `maxGroupFitted`/`maxTypeFitted`. That removes ~60-70 % of the choices. `OPT_NO_PRUNE=1` keeps all.
    - **Moves**, each screened with a SearchPlan built for it: one position (a fitted module or an empty slot) to any choice of its rack or empty (one plan per position over all choices, chunked); else pair moves: the one-move effects against the current set are added up, and the `refinePairs` (256) pairs with the best estimated goal that are estimated to fit (0.5 % slack) are evaluated exactly (one plan per position pair). The best screened move is accepted if its **canonical** evaluation (`Engine::evaluate` of the pinned modules followed by the set in rack and candidate order, memoized per set) beats the current set by `better` (valid, fits, goal bucket, price), a strict weak order, so the descent ends.
    - **Exact pass** (small requests): when the open slots have at most `refineExact` (3e7) combinations of the pruned choices and the enumeration needs at most 20k plans, every combination is evaluated exactly (`enumerate`, the same code as the member brute force) and its best fitting set becomes the first start. Up to ~5 s at 16 threads for 27M combinations; 2-3 open slots are mostly well under 1 s.
    - **Phase 1**: steepest descent from stage 2's best distinct end sets (`refineStarts`, 0 = max(chains, 8)), in parallel. If none fits (or stage 1's model hit a size limit, below), from the empty set.
    - **Phase 2**: iterated local search on 16 chains (`refineChains`, fixed so results don't depend on the thread count), started from the best phase-1 local optima. Each round perturbs every chain's set and descends again; a chain keeps the result if better. Perturbation: half the time a guided kick (one of the 32 strongest one-move neighbours by goal that didn't improve the set, mostly an upgrade that doesn't fit, which the descent then pays for with pair moves, plus 0-1 random changes), else 1-3 random positions to random choices. Seeds depend on (chain, round) only. It stops when `refinePatience` (800) chain iterations bring no better best set ("converged"), at the time budget (`timeBudget`, default 60 s for the whole run; "time"), or after `refineRounds` ("rounds"). Every local optimum found joins the end sets; the report takes the best fitting distinct ones (`report()`).
    - **Model limits**: a `ModelLimit` exception (too many kinds for a record key, the core plan, a projection key) skips stages 1 and 2, and refine searches alone from the empty set (`stats.modelSkipped`).
    - Progress: `refine` at 0.80, then `refine: round N, best G` per round.
12. **Infeasibility** (`Result::infeasible`, response `status: "infeasible"`, see `OPTIMIZER_CLI.md`). An open slot may stay empty, so only the pinned part (the open slots empty) can make every choice unfittable. When it is over on CPU, power or calibration:
    - **calibration**, right after `setup()`: nothing raises calibration output or lowers a rig's calibration cost, and open rig slots only add rigs, so pinned calibration > output ends the run at once (no candidates, ~5 ms). The message names the pinned rigs whose removal alone fixes it (else all pinned rigs).
    - **outputs**, after `measure()`: per open slot the strongest allowed output gain, compounded as a multiplier, and separately the largest drop of the pinned modules' needs (`Candidate::pinnedDrop`), added up. If the pinned need minus the drops is still above the raised output (pad 1e-6 relative + 0.01), no set fits. It is a necessary condition: it never rejects a fittable case.
    - **search**: otherwise stages 1, 2 and refine run (refine from the empty set when stage 2 found no fitting set); if no fitting set is found and no fitting-module fill alone makes the pinned part fit, the reason is "search", with the bounds above in the message. It is not a proof (refine is a local search); "calibration" and "outputs" are.
    - **capacitor**: sets fit CPU, power and calibration, but none found meets `requireCapStable` / `minCapRecharge`.
    - If some choice fits but none has a goal above 0, the status stays `ok` with no options and a warning.
    - With `bruteForce` (`--check`) the fast exits are skipped, so the brute force can confirm the diagnosis (feasible = 0); the response still has the infeasible status.
13. **Threads and caches**: `Pool` (fixed workers, `run(n, grain, fn)`, optionally guided chunks; the caller is worker 0; not reentrant, so nothing inside a parallel loop starts another). `Cache<V>`: sharded open addressing over atomic node pointers. Lookups take no lock; a key is computed once (`std::call_once` per entry; other threads wait), so values are pure functions of their key and results don't depend on timing. Resist records and orders have their own lock-free publication (item 8). Results are deterministic and independent of the thread count unless the time budget stops stage 1 or refine (`stats.stage1Stopped`, `stats.refineStop == "time"`); `--refine-rounds N` with `--time-budget 0` gives a fixed-work mode for tests. Stats like `engineCalls` can vary slightly between runs.

**Module rules** (`excludedFromSearch`, `clampPinnedState`; add similar rules there): assault damage controls (effect 7012) are never candidates, since their active bonus lasts ~12 s and a regular damage control is always better; pinned ones are evaluated at most online.

## 3. Checking the optimizer

- **Stage 1 brute force** (`Options::bruteForce`; `--optimize-check`, `--optimize-request --check`): after stage 1, `Search::bruteForce()` enumerates every combination of the stage-1 kinds (per rack, every multiset of core + resist representatives within the slot count, kind caps and group limits, empty slots included), each evaluated exactly with one SearchPlan holding all kinds of each rack in every slot, in parallel. A set that doesn't fit gets the first fitting-module fill (fewest modules first) that fits, also exact; the goal must not change (`fittingGoalChanges`). The feasible combinations (goal > 0) sorted by exact goal must equal stage 1's top-K model scores rank by rank (relative 1e-5), and stage 1 must keep min(K, feasible) sets. A set the bounds or prefilters lost shows as a lower score at some rank. Stage 2 and refine are skipped. Keep cases small with `--slots` (the default 2/2/1/2 is fast; 3/3/2 is up to 77M combinations, ~30 s).
- **Member brute force** (`Options::memberBruteForce`, `--members`; `Search::enumerate`): every combination of every module choice of the open slots (all members and charges, unpruned), exact; the reference for refine. Fine for 2-3 open slots, sometimes 4; it gives up beyond 5e9 combinations.
- **Debug switches** (environment): `OPT_RESIST_VERIFY=1` (evaluate every resist set at table build and check its bound), `OPT_NO_ANALYTIC=1` (exact resist tables), `OPT_NO_FITPRUNE=1`, `OPT_RACK_ORDER=low,rig,...`, `OPT_NO_RIG_CAL_SPLIT=1` (one subgroup per rig family), `OPT_NO_PRUNE=1` (refine keeps dominated choices), `OPT_NO_CHARGE_ALTS=1`, `OPT_REFINE_FROM_EMPTY=1`, `OPT_KICK` (percent of guided kicks, default 50), `OPT_ACCEPT` (percent of worse local optima a chain moves to, default 0).
- The commands to run after changes are in `README.md`, "Validation".

## 4. pyfa integration

**Use**: select one or more high, mid, low or rig slots in the fitting view (modules or empty slots; shift/ctrl-click), right-click, **Optimize Modules (N slots)...**. The window shows the slots; pick the goal, the constraints (max price per module, officer modules, ancillary repairers, cap boosters, max repairers, cap stable, min cap recharge, the target resists for balanced goals), the number of results and the max time, then **Run**. A gauge shows the exe's progress lines; **Cancel** kills the process. Results: one row per option (goal, gain, price, price change, CPU, PG, calibration, cap used / recharge, fits, the changed modules with counts); the first row ("now") is the fit as it was. Click a column header to sort. Selecting a row lists what goes into each slot. **Double-click (or Enter) fits the option** as one undoable step; the window stays open, so another option can be applied on top, and the "now" row puts the original modules back. Warnings from the response are shown above the table; for `clampedModules` a **Set them online** button sets them online. When nothing can fit, the window shows "No option can fit." with the diagnosis. **Optimizer path...** chooses the exe.

Files:
- `service/moduleOptimizer.py` (no wx): `buildRequest(fit, positions, goal, ...)` writes the request from the Fit (ship, mode, character, `fit.appliedImplants`, boosters with active side effects, every `fit.modules` entry with position = list index, state, charge, mutations, `optimize` for the selected positions). Character: none for All 5, `defaultLevel 0` and no skills for All 0, otherwise `defaultLevel 0` plus every skill the character has above 0 (which includes alpha clone caps). Prices: all rows of pyfa's `prices` table with price > 0 are always sent, so the exe never opens saveddata. `parseResponse` -> `OptimizerResult` / `Option` / `SlotChoice` / `FitStats`. `OptimizerRun` runs `PyfaReader.exe --game <eve.db> --optimize-request - --out -` with `CREATE_NO_WINDOW` on Windows, reads `progress` lines from stderr, cancel = kill, timeout, error response / exit code / non-JSON output -> `OptimizerError`. `fitMatchesRequest` checks that the pinned modules are unchanged before applying.
- `gui/moduleOptimizerDialog.py`: the window (`wx.Frame`, float on parent, one at a time). The run is a daemon thread; progress and results come back with `wx.CallAfter`. Unchanged slots of an option are applied from a `ModuleInfo` snapshot taken at Run time, so a mutated module that stays keeps its mutations.
- `gui/fitCommands/gui/localModule/optimizerApply.py`: `GuiApplyOptimizedModulesCommand(fitID, {position: ModuleInfo or None})`: frees every changed slot first, then fills them (`CalcReplaceLocalModuleCommand`, restrictions checked), so group limits can't trip on the way; undo restores everything.
- `gui/builtinContextMenus/moduleOptimize.py` (registered after `moduleFill`).
- `service/settings.py`: `ModuleOptimizerSettings` (`exePath` ('' = `<pyfa root>/cpp/bin/Release/PyfaReader.exe`), `goal`, the constraints, `results`, `timeBudget` (60), `threads` (0 = all; no UI), `timeout` (300 s; raised to at least the budget + 120 s, none with no budget)).
- `cpp/tools/optimizer_dialog_test.py`: drives the dialog end to end with pyfa's real MainFrame on a temporary copy of saveddata.db.

**Windows install** (`scripts/build_pyfa.ps1`, `pyfa.spec`): the exe is bundled into `cpp/bin/Release` of the install when it exists at build time. It needs `effect_modifiers.tsv` and `warfare_buffs.tsv` next to it (the MSBuild build copies them; `pyfa.spec` bundles them) The Release build links the C runtime statically (`/MT`), so no Visual C++ redistributable is needed. eve.db is passed with `--game`.

**WSL**: pyfa running under WSL runs the Windows exe through interop; paths given to the exe are converted with `wslpath -w`. SQLite can't open a database inside the WSL file system from Windows (`\\wsl.localhost\...` gives "database is locked"), so when pyfa's eve.db isn't under `/mnt/`, `--game` is left out and the exe uses the eve.db it finds next to/above itself (the repo's `eve.db` for `cpp/bin/Release`). It should be the same game data version as pyfa's.

## 5. Performance

Stage 1 seconds, 16 threads (Ryzen 7 7800X3D), Release, `timeBudget` 0, prices frozen in the request:

| Case | Stage 1 | Best |
|---|---|---|
| Proteus 458 `localArmorRemoteArmor` (16 open slots incl. 5 highs) | 4.8 s | 1705.57 |
| Proteus 458 `armorActive` / `armorRemote` (same slots) | 0.58 / 0.80 s | 2612.42 / 451.86 |
| Absolution 3411 `armorActive`, whole racks | 2.68 s | 4120.28 |
| Myrmidon 2593 `armorActive`, whole racks | 2.54 s | 3447.46 |
| Abaddon 910 `armorPassive`, whole racks | 4.86 s (resist tables) | 473899.7 |
| Cyclone 3347 `shieldActive`, whole racks | 2.34 s | 4250.44 |
| Osprey 78 `shieldRemote` / `shieldActive`, all racks + highs | 1.90 / 3.23 s | 587.88 / 2064.96 |

Refine adds ~0.5-1 s on small requests and 1-10 s on whole racks at 16 threads (5-37 s at 1 thread); small requests (2-3 open slots) take ~0.3-1.3 s in total.

`tools/sample_profile.py` samples the exe's stacks (Windows Python, uses the Release build's PDB).

## 6. Known limits and open problems

- **Refine is a local search.** It is not a proof of optimality on whole racks. It reached the best known set on all 19 large test cases and on every small request checked against the member brute force (197 with 2-3 open slots, 20 with 4); a 3-position exhaustive check around each large result found nothing better. Larger requests that are still small (4 open slots with big mid pools) are only covered by the iterated search.
- **The pruning rule is a dominance heuristic**: a module that is weaker on every measured stat but helps through an unmeasured interaction would be lost. None is known.
- **Stage 1 sees subgroup representatives only**, so its feasibility (and `--check`'s) is decided over representatives; refine makes the final answer member-level.
- **Balanced goals on big racks**: Osprey 78 `localShieldRemoteShield` with all racks + highs (4.2e11 core sets) doesn't finish stage 1 in minutes; with the default budget stage 1 stops at 30 s and refine gives the result. The dive's first cutoff is poor and level-3 nodes whose low children never fit cost most of the time: `partialFits` treats the free low rack as full of output modules and `fixedFits` is skipped because core lows change outputs. Ideas: a fitting bound with output-changing kinds in free racks (`fitSlack` maximized over the free racks' projections of `inflFit_` kinds), a better incumbent, a joint bound for the two sides of a balanced goal (same slot split, CPU/power shared), choosing the rack order per request (e.g. Knuth's tree-size estimator), a smaller top-K for large searches.
- The "outputs" infeasibility bound treats CPU and power separately: two open lows that would need a co-processor *and* a power module are decided by the search.
- **Resist bounds rely on the composition model.** Every set used is evaluated exactly and checked against its bound. The RAH vertex bound assumes the adaptation conserves the RAH's total resist, which holds for the uniform profile; revisit if non-uniform damage profiles are added.
- `Pool::run` is not reentrant: table builds triggered inside parallel loops run on one thread, and siblings waiting for the same table idle (Abaddon).
- Key limits: `packCounts` keys hold at most 32 kinds of 4-bit counts, projection keys at most 125 kinds (`ModelLimit`, refine then runs alone).
- The subgroup size token comes from names (`'Micro' Cap Battery` gets no size). Harmless but splits a subgroup.
- Group limits shared across roles are checked per set; `maxTypeFitted` for variants only in stage 2 and refine.
- Prices are pyfa's cached ones; nothing is fetched before a run. 0 or missing = no price (skipped with a price cap, counts as 0 otherwise).
- pyfa: results are for the fit at Run time; applying checks the pinned modules (type, charge, state) but not drones, implants or the character. Applying sets the states the response gives (active / online); spool and RAH pattern settings of replaced modules are not kept. Stage 1 reports no progress steps (the bar waits at 0.25). The dialog has no translations yet (strings go through `_t`).
